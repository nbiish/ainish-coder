finding: `ainish-rag secrets` reports a direct provider as "up" when only its public model catalogue is reachable, so a step with no usable key looks healthy while its chat path would 401.
evidence: `probe_health` builds `<base>/models` and treats any non-401/403 answer as reachable ("the host answered HTTP at all, not that it served a catalogue" — a deliberate, documented choice). OpenRouter serves `/api/v1/models` **publicly**, so it answered 200 with no credential and reported `up`, while the same base with no key returns `401 {"message":"Missing Authentication header"}` on `/chat/completions`. Measured live 2026-11-13 for the three direct steps: `openrouter` up / `zai` down (401 on catalogue) / `xiaomi-mimo` down (401 on catalogue) — yet with the vault locked, `resolve_driver_key` returned None for all three, so all three would have skipped. The report therefore showed one step as usable that had no key at all.
options: (a) when a probe returns a catalogue without auth, issue one tiny authenticated chat call (`max_tokens: 1`) to confirm the step can actually answer — costs a request per `secrets` run, so gate it behind a flag; (b) report catalogue reachability and auth readiness as two separate fields (`reachable`, `auth_ok`) instead of collapsing them into "up/down"; (c) leave it and document that `up` means "endpoint answers", not "this step will work". (b) is the honest fix and costs nothing; (a) is the strongest but should not run by default. (c) alone is what today's wording already implies to nobody.
scope: pre-existing and independent of the chain reorder — the same conflation applied to the old six direct steps. Recorded because a green "up" on a step that cannot authenticate is exactly the kind of report that makes an operator stop looking.
