finding: `src/rag` ships two engines that both answer the `ainish-rag` CLI, and they implement DIFFERENT generations of the product — the Obsidian vault renderer exists only in the Rust crate, which is the one that never runs on a standard host.
evidence: `bin/ainish-rag:69` hard-codes `PY_ONLY_SUBCOMMANDS=" context secrets "`, so `context`/`secrets` always route to `src/rag/rag.py`. No `bin/ainish-rag-darwin`, `bin/ainish-rag-linux`, or `bin/ainish-rag.exe` exists, so `NATIVE_BIN` is always empty and `src/rag/target/release/ainish-rag` is never selected by the launcher. Commit `788602f` ("make the wiki an Obsidian vault") added the vault renderer to `wiki.rs` (+352 lines) and the wikilink READER to `rag.py` (+89), but never the vault WRITER to `rag.py`. Net effect on a default host: retrieval understands the vault, generation cannot produce it, and until this change generation actively destroyed it. `llms.txt:321,334` described the pair as one crate "and companion rag.py", which reads as Rust-primary and is how a plan came to scope engine work to code that never answers a request.
options: (a) port the vault writer into `rag.py` so the reachable engine is complete, and keep the crate as a performance mirror — the vault format is one template plus wikilinks, so this is small and it removes the split permanently; (b) ship the native binary (`deploy_rules_sync.sh` already knows `target/release/ainish-rag`, it is simply never copied to `bin/`, and no CI job builds per-platform); (c) keep the current split, with `rag.py` refusing to touch vault pages (done) — correct but leaves `wiki` unusable from the default engine on a vault repo. (a) is the durable fix; (b) is required anyway if the native path is meant to be used.
scope: pre-existing and architectural. Recorded because it is a trap that produced a wrong plan, and because the operator's stated direction (Obsidian wiki + `.agents/` context folders, no embedding model) is only fully implemented in the engine nobody runs.
