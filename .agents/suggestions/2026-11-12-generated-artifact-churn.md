finding: `ainish-rag wiki` from the Python engine silently DOWNGRADES an Obsidian vault to plain markdown — stripping frontmatter, aliases, tags, and every `[[wikilink]]`. FIXED in this change (fail-closed guard); this file records the reasoning and the remaining architectural split.
evidence: the vault renderer exists ONLY in the Rust crate — `src/rag/src/wiki.rs:31` (`WIKI_TAGS_ROOT = "ainish/wiki"`), `:39-57` (the frontmatter template), `:1094` (the test asserting tags). `src/rag/rag.py` has ZERO occurrences of `ainish/wiki`; its `generate_wiki` emits plain `# title` markdown. Both engines answer `ainish-rag`, and `bin/ainish-rag:69` routes plain invocations to Python (no `bin/ainish-rag-{darwin,linux}`/`.exe` exists), so the reachable `wiki` command is the one that cannot produce a vault. Measured on a copy of this repo's own pages: committed `README.md` has 11 `[[wikilinks]]`; after `ainish-rag wiki --no-index` it has 0 and no frontmatter. That is a silent downgrade of the exact surface the operator says retrieval now depends on.
fix applied: `rag.py generate_wiki` now detects pages carrying the `ainish/wiki` tag and REFUSES (SystemExit with the reason and the correct command) rather than overwriting them. Non-vault repos still generate normally; verified both ways.
remaining split: the vault generator is native-only. That needs a decision — see `.agents/suggestions/2026-11-12-rag-engine-authority-unstated.md`.
related: the same run also showed `wiki` hard-requiring the embedding model. Fixed by making `--index` opt-in in both engines (it was `default_value_t = true` in Rust, which in clap 4 is a flag that can only ever be true, and `--no-index` in Python with indexing default-on).
