finding: running the RAG engine from a subdirectory writes a full `.agents/` tree there — including a private ML-DSA-65 signing key and a session PSK — and none of it was gitignored, because every ignore rule was root-anchored.
evidence: `ainish-rag wiki` (and any command that touches the identity root) creates `.agents/{rag,audit,wiki}` relative to the path it is given. Running it from `src/rag/` during this task produced `src/rag/.agents/audit/signer.mldsa65.priv`, `src/rag/.agents/rag/session.psk`, and seven generated wiki pages. `.gitignore` entries for this state are root-anchored (`.agents/rag/*`, `.agents/comms/*.live.txt`), so `src/rag/.agents/...` matched nothing and `git add -A` staged the whole tree, private key included. It was caught only because the staged-file list was read before committing. The same mechanism is how `.agents/comms/2026-11-12-identity-guard.live.txt` came to be tracked on `main`: the pattern was `*-team.live.*`, which does not match a live board with a different prefix.
fix applied: `.gitignore` now ignores `src/rag/.agents/`, `skills-to-distribute/**/.agents/`, and `**/.agents/{rag,audit,wiki}/`, and the comms live-board pattern widened to `*.live.{txt,md}`. Verified both directions — the nested key path is ignored, the root `.agents/` stays tracked — and pinned by an assertion in `scripts/test-pqc-dist.sh`.
options: (a) keep the path-based ignores (done) and additionally make the engine refuse to initialize an identity root outside the repository root it was told to manage, which removes the cause rather than the symptom; (b) add a pre-commit secret scan that covers `.priv`/`.psk` regardless of path — the existing local secret scan did not flag `signer.mldsa65.priv`; (c) both. (a) is the real fix: a nested `.agents/` is engine output in the wrong tree, and writing keys there is a key-material handling defect, not just an ignore-rule gap.
